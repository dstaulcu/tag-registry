# Specification

This is the contract between a tag registry repository and the clients that read it. The key words MUST, SHOULD and MAY are used in the RFC 2119 sense. The reference producer is [`scripts/build-manifest.mjs`](../scripts/build-manifest.mjs); if this document and that script disagree, the script wins and this document has a bug.

## 1. Repository layout

```
core/<facet>/<name>.md
teams/<team>/team.md
teams/<team>/<facet>/<name>.md
teams/<team>/<sub-team>/team.md        # teams nest to any depth
teams/<team>/<sub-team>/<facet>/<name>.md
registry.json                          # generated manifest
```

- A tag is one markdown note. Its tag is `<facet>/<name>`, taken from the folder and file name.
- `core/` holds the facets and tags shared by everyone. A folder directly under `core/` MUST be a facet.
- A folder under `teams/` (or under another team) that contains a `team.md` is a team. Its **id is its folder path** below `teams/`, for example `example-org/example-component`. A folder in a team that is neither a facet nor a team (no `team.md`) is an error.
- Facets are defined by the registry and listed in the manifest. Teams add values under existing facets; they cannot add facets.

## 2. Tag notes

Each note starts with front matter:

```yaml
---
tag: area/finance
aliases: ["#area/finance"]
facet: area
status: active        # active | proposed | deprecated
replaced_by:          # required when status is deprecated
owner: core           # core, or the owning team id
---
```

and contains a line `Definition: <one line>` in the body.

Rules the producer enforces:

- `tag` equals `<facet>/<filename without .md>`, and `facet` equals the folder.
- `name` is lowercase, hyphen-separated, no spaces (`^[a-z0-9]+(-[a-z0-9]+)*$`). Team folder names follow the same rule.
- `aliases` is exactly `["#<tag>"]`, so Tag Wrangler treats the note as the tag page.
- `status` is one of `active`, `proposed`, `deprecated`. A deprecated tag MUST name an existing `replaced_by`.
- A tag is defined once across core and all teams.
- Notes use LF line endings.
- Tags are never deleted. They are deprecated.

## 3. Manifest (`registry.json`, version 2)

The manifest is generated by `npm run manifest` and checked in CI. It is served from the repository root. Real excerpt:

```json
{
  "version": 2,
  "facets": ["area", "with", "objective", "project", "technique", "tool"],
  "teams": [
    {
      "id": "example-org/example-component",
      "name": "Example Component",
      "description": "Placeholder second tier with sample tags.",
      "level": "component",
      "parent": "example-org",
      "example": true
    }
  ],
  "tags": [
    {
      "tag": "area/finance",
      "facet": "area",
      "source": "core",
      "status": "active",
      "replaced_by": null,
      "aliases": ["#area/finance"],
      "definition": "Money, budgeting, taxes and purchases.",
      "path": "core/area/finance.md",
      "hash": "250cbf68cd37709e5ad4b2558b99d47dae20c21ba749ef7aadab159d04ca4372"
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `version` | Manifest format. Clients MUST refuse a version they do not know. |
| `facets` | The allowed facet names. |
| `teams[].id` | Folder path of the team, `/`-separated. |
| `teams[].name`, `description` | From `team.md`; `name` falls back to the folder name. |
| `teams[].level` | Free-text tier name (directorate, branch, ...). Display only. |
| `teams[].parent` | Parent team id, or `null` for a top-level team. |
| `teams[].example` | `true` for placeholder teams. Clients SHOULD hide them by default. |
| `tags[].tag` | Full tag, `<facet>/<name>`, without `#`. |
| `tags[].source` | `core` or the id of the team that owns the tag. |
| `tags[].replaced_by` | Full tag or `null`. |
| `tags[].definition` | The `Definition:` line, possibly empty. |
| `tags[].path` | Repo-relative path of the note. |
| `tags[].hash` | SHA-256 (hex) of the note's exact UTF-8 text. |

Clients MUST read `facet` and `source` from the manifest and MUST NOT derive them from `path`; with nested teams the path no longer has a fixed shape.

## 4. Visibility and inheritance

A team's tags are visible to that team and to every team below it (`parent` chain). Core is visible to all. Choosing which teams to subscribe to is a client concern; a client that lets a user pick a team SHOULD offer to include its ancestors.

## 5. Versioning

- Adding a tag, team or facet does not change `version`.
- Adding an optional manifest field does not change `version`. Clients MUST ignore fields they do not know.
- Removing or renaming a manifest field, or changing how `hash` is computed, bumps `version`.
- Vocabulary changes are tagged as repository releases (`vX.Y`).

## 6. Federation

A registry MAY be split across repositories. Each source publishes a manifest in this format, and a consumer MAY merge several. On a duplicate tag the earlier-configured source wins. The tag-uniqueness rule applies within one repository; across sources it is the consumer's job to resolve conflicts.
