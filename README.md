# tag-registry

A shared vocabulary of tags, kept in one repository, so people, teams and automated agents describe their work the same way. Consistent tags let you search, filter and roll up work across notes, tools and teams, at home or at work, without everyone retagging by hand.

Any tool can read the registry: it is plain markdown notes plus a JSON manifest. [Obsidian](https://obsidian.md) is the first integration, via the [Tag Registry Client](https://github.com/dstaulcu/obsidian-tag-registry-client) plugin (see the [showcase](docs/showcase.md)), but nothing here depends on it. APIs, MCP tools or internal mirrors may serve the same manifest; this repo is the source.

**New here?** Read [why a shared tag registry helps](docs/why.md). **Building something?** Start with the [specification](docs/specification.md) and the [docs index](docs/README.md).

## Facets

Every tag is `<facet>/<name>`. Each facet answers a different question about a piece of work, and the set of facets can grow over time; the manifest's `facets` list is authoritative. Current core facets:

| Facet | Tag | Meaning |
| --- | --- | --- |
| area | `#area/<domain>` | Life domain: home, work, health, fitness, finance, learning |
| with | `#with/<who>` | Who the effort involves |
| objective | `#objective/<goal>` | A goal or direction that projects serve |
| project | `#project/<name>` | A project or initiative, including a trip |
| technique | `#technique/<capability>` | A capability or method, independent of tool |
| tool | `#tool/<name>` | A named tool, service, software, product or system you use |

## Layout
```
core/
  facets.md              # defines the facets
  area/<name>.md         # home, work, health, ...
  with/<name>.md         # generic kinds only (family, team, customer)
  technique/<name>.md    # cross-team examples
  tool/<name>.md
teams/<team>/                  # teams nest to any depth: teams/<team>/<sub-team>/...
  team.md                # name, description, level, owners
  project/<name>.md
  area/<name>.md         # other facet folders are allowed too, e.g. with/<party>
  <sub-team>/team.md     # a folder with a team.md is a child team
.github/CODEOWNERS       # core/ -> core group; each team folder -> that team
scripts/build-manifest.mjs
registry.json            # generated manifest (version 2)
```
- The core defines the facets and a few cross-team examples. Changes go through the core group.
- Teams add values under existing facets in their own folder. A new facet must be proposed to the core.
- Teams model any hierarchy. A team id is its folder path (for example `example-org/example-component`; deeper nesting works the same way) and `level` in `team.md` is free text, so name the tiers whatever your organization does (directorate, center, department, branch, ...). Tags in a team are visible to every team below it. `teams/example-org/` is a placeholder tree: copy it, rename the levels and remove `example: true`.
- A team tag used by several teams can be promoted into `core/` (move the note, keep the tag name).

Each tag is one note named `<name>.md`. The `aliases` front matter equals the tag (for example `["#technique/job-scheduling"]`) so Tag Wrangler treats the note as the tag page.

## Naming rules
- Lowercase, hyphen-separated, no spaces.
- Techniques are named by capability, not tool.
- Tools are named by the name of the service, software, product or system itself, not by a project that uses it.
- Named people and organizations go under `teams/<team>/with/`, never in core.
- Tag names are unique across core and all teams.
- Never delete a tag. Mark it `status: deprecated` and set `replaced_by`.

## Note format
```
---
tag: technique/job-scheduling
aliases: ["#technique/job-scheduling"]
facet: technique
status: active        # active | proposed | deprecated
replaced_by:          # for deprecated tags
owner: core   # core, or the owning team id
---

# technique/job-scheduling

Definition: one line.

Use when: ...                       # optional
Don't use when: ...                # optional
Related: [[tool/github]]           # optional
```

Only `Definition:` is required. Add `Use when:`, `Don't use when:` or `Related:` lines only when they say something; do not leave them empty.

## Manifest (version 2)
`registry.json` is generated by `npm run manifest` and checked in CI (`npm run check`). It contains:
- `facets`: the facet names.
- `teams`: `{ id, name, description, level, parent, example }` for each team. `parent` is the parent team id (or null) so tools can show a hierarchy picker and inherit parent tags; tools should hide teams with `example: true`.
- `tags`: `{ tag, facet, source, status, replaced_by, aliases, definition, path, hash }` for every tag. `source` is `core` or the team id; `hash` is the sha256 of the note.

Consumers fetch the manifest over HTTPS, keep the core plus the teams they chose, and may merge more than one source in this format (for example an internal or private registry that needs authentication).

## Stage two: federation
If one repo is outgrown, each team gets its own repo from a template. The core repo keeps the facets and a list of team repo locations, and an aggregator still produces one combined manifest in the format above, so consuming tools do not change.
